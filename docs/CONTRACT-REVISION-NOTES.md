# Contract revision notes, build of 30 October 2026

Proposed revision note for `01-PRODUCT-CONTRACT.md` (deliverable 1), to be appended at sign-off. The contract is not yet signed, so it has not been edited. Each item is a default the contract marked **Proposed** that the build changed, or a behaviour the contract left open that the build had to fix. Section numbers refer to the contract.

| # | Section | Contract said | Built as | Why |
|---|---|---|---|---|
| 1 | 4, F1 | Own host only; private and loopback addresses refused | Adds `MLTSA_ALLOW_PRIVATE_SELF`, off by default. When set, only the site's own host may resolve to loopback or a private address. Metadata and link-local addresses are always refused. The Health screen warns while it is set | Development and test sites run on loopback; without it the plugin cannot be tested locally |
| 2 | 4, F6 | Drop query strings by default | Query strings are dropped from sitemap and recheck URLs. Permalinks WordPress generates itself keep theirs (`?p=12`), still subject to the request policy (no action, nonce, REST or logout queries) | Sites with plain permalinks would otherwise audit the homepage in place of every post |
| 3 | 4 | Retries: 2 for transient failures | 2 retries with backoff for transport errors and HTTP 429, 502, 503, 504. A timeout is not retried | A timeout already held a PHP worker for the full timeout; retrying triples the load on a struggling shared server |
| 4 | 4 | Fetch limits | Unchanged (2,000 URLs, one request at a time, 1 second gap, 15 second timeout, 5 redirects, 5 MB). Backing off when slow means: after a response slower than 3 seconds, wait as many seconds as it took, up to 10. A URL whose fetch was attempted 3 times without finishing (the process died) is recorded as an error | Makes "backs off when the site responds slowly" testable, and stops one bad page stalling a run for ever |
| 5 | 3, F4 | Size-capped raw JSON-LD; depth 64 | Analysis caps: 1 MB per block parsed, 64 KB of raw JSON-LD stored per block, depth 64, 5,000 entities per page, 200 distinct resources checked per run | Bounds memory and storage per run on a shared server |
| 6 | 3 | One row per rule outcome per run | Only non-pass outcomes are stored. A pass is the absence of a finding on a page read under a known rule version (the run stores each rule's version) | Storing every pass would multiply storage by the number of rules for no audit value |
| 7 | 4 | Excluded content recorded with its reason | Password-protected posts, denied paths, off-site URLs and URLs over the cap are stored one row each with a reason. Drafts, pending, private and scheduled posts are never queried; their counts are stored on the run | Querying non-public content to record it would read content the audit must not touch |
| 8 | 6, 8 | Later runs compare with the last successful comparable monthly run | Monthly runs compare with the last complete or partial monthly run; manual runs with the last complete or partial monthly or manual run; rechecks do not compare. A partial baseline is safe because only a page read in both runs can show an issue as resolved | Otherwise one timed-out page every month would leave a site with no baseline |
| 9 | 8 | Email only when something meaningful changed, or a run is partial or failed | Also on the first completed monthly run ("first audit complete"), since it establishes the baseline. No email for a cancelled run | Recipients need to know monitoring has started |
| 10 | 8 | Kill switch stops scheduling and mail immediately | The setting also cancels a monthly run in progress before its next request. Manual runs continue. The constant stops everything, manual runs included | "Immediately" needs a defined effect on a run already going |
| 11 | 8 | Recipients start empty | At most 10 recipients | Limits the damage of a mistaken list; can be raised later |
| 12 | 8, M3 | Recipients confirmed against the home URL | Any change to the recipient list confirms it on the current home URL. Reconfirming the same list after a migration is a separate, logged action | Makes the clone pause and its release auditable |
| 13 | 2 | No other endpoints named | Two additions: an `admin-ajax` action that moves an audit along while its screen is open (capability and nonce checked, 8 second budget), and WP-CLI commands `wp mltsa tick`, `audit` and `status` for server cron. No REST routes | Manual audits must finish where WordPress cron is slow or disabled |
| 14 | 11 | Retention: Proposed 13 monthly baselines minimum | At least 13 monthly runs and 13 other runs keep full evidence. Older runs lose their pages, blocks and findings; the run row stays as a record. The run the next comparison will use, and any run holding the latest evidence for a finding not resolved or marked a false positive, are never purged | The contract counted monthly runs only; manual runs and rechecks would otherwise grow without limit |
| 15 | 9 | Reactivation rebuilds the next scheduled occurrence only | Deactivation also forgets when monitoring started, so a reactivation never runs a catch-up for a month missed while the plugin was off | A catch-up after reactivation would be a backlog run |
| 16 | 5 | Rules per contract and plan | Rule set 2026.10.2: 52 rules. SITE-001 (same business @id with different details on different pages) is a review, not a fail, as the defect catalogue requires. ID-003 (reference to an undefined entity) is judged across the site, not per page | Fixture set from the July and August evidence |
| 17 | 7 | Each CSV downloads on its own | As specified, plus: every cell quoted, UTF-8 with a byte-order mark, and the ZIP built in memory by the plugin's own writer | `ZipArchive` needs a file on disk, which section 1 forbids |
| 18 | 4, F6 | Never request admin, login, XML-RPC or REST routes; the build also refused all of `/wp-content/` and `/wp-includes/` | Page fetches still refuse both folders. Image and logo checks (URL-004) may request static image, PDF and video files there (extension at the end of the path, no script extension anywhere in it), checked on every redirect hop | Otherwise no image in the media library is ever checked, so URL-004 cannot work on a WordPress site (review finding 3, 30 October 2026) |
| 19 | 4 | Timeout per request (default 15 seconds) | The timeout is the lower of the setting and the time left in the worker's slice. A request the slice cut short is retried in the next slice, and recorded as a timeout only on its third try. Each tick queues its own continuation before working, and an hourly watchdog requeues a worker for a stranded run | A request started near the end of a slice could outlive the PHP time limit and kill the worker, leaving the audit stranded with nothing scheduled (review finding 4, 30 October 2026) |
| 20 | 6 | A new or changed rule is labelled as a rule change, not a website change | The digest and the audit screen now also count findings that stopped appearing because their rule was removed or changed ("not a fix") and evidence changes under a changed rule, in two new lines. The comparison treats a removed rule as a rule change, as the register already did | The digest called findings of a removed rule "No longer detected" while the register held them (review finding 7, 30 October 2026) |
| 21 | 6 | The issue register holds one row per underlying issue across runs (section 5 data model); the contract named no screen for it | A new Issue register screen lists every issue across all audits from current issue state, with the latest evidence, and filters for status, verification state, owner and search. The Findings screen keeps showing one audit's occurrences and links to it | The Findings screen defaulted to the latest finished run, so issues that run did not cover disappeared from the default view (review finding 9, 30 October 2026) |
| 22 | 5 | Rules per contract and plan (row 16: rule set 2026.10.2, where URL-004 also checked own-host `sameAs` pages) | Rule set 2026.11.1: URL-004 version 3 checks own-host `image`, `logo`, `thumbnailUrl` and `contentUrl` values only. An own-host `sameAs` link that returns 404 is no longer reported, so pilot defect D44 (a founder's profile page on the firm's own site returning 404) is not detected. Open URL-004 issues for a `sameAs` link are held as a rule change, not cleared as fixed | URL-004 is reported as a broken image or file; a broken page link reported that way misleads staff. A link rule for own-host pages would be a contract change, so none was added (review reply, 2 November 2026) |
| 23 | 6, 7 | Unavailable is a verification state set only by the scanner (section 6); nothing on how often it repeats | Each audit also reports a read-only coverage figure for findings: the number held as Unavailable in that audit, the number Unavailable in 2 or more audits in a row (with links on the audit screen and issue IDs in the export Summary) and the longest run. Counting starts with the first audit after this change | An issue that cannot be read month after month otherwise looks like a stable result, not a gap in coverage (review reply, 2 November 2026) |
| 24 | 4, 5 | Rules per row 22 (rule set 2026.11.1: own-host `sameAs` pages not checked); requests go to the site's own host only (section 4) | Rule set 2026.11.2 adds URL-008 "Profile link on this site returns not found" (medium, confirmed errors): own-host `sameAs` links are requested once per audit as pages, under the normal page request policy (not the wider static-file policy of URL-004), with the same per-audit limit (200, shared with images and files), slice budget, deferral and "unavailable" handling as URL-004. Only 404 and 410 are reported. `sameAs` links to other hosts are never requested. Pilot defect D44 is detected again. The audit screen and export count images, logos and profile links together | URL-004 reports images and files only (row 22), which lost D44 (a founder's profile page on the firm's own site returning 404). A separate page rule keeps both labels accurate (owner decision, 2 November 2026) |
| 25 | 2, 4 | Timeout per request (default 15 seconds); per row 19, the lower of the setting and the time left in the slice; per row 13, an 8 second budget for the audit screen's step | A request starts only when the slice has the full timeout left, and is never shortened, so a timeout always means the site took longer than the setting. Each slice (WordPress cron, the audit screen's step, WP-CLI) is raised to at least the timeout plus 2 seconds, so the audit screen's step can run up to 17 seconds at the default. A URL deferred for lack of time is retried in the next slice without counting; a deferral counts only when the URL had the whole slice (a redirect chain or retries longer than a slice) and the third such is recorded as an error (`budget_spent`). Where the PHP time limit cannot fit the setting (limit less 10 seconds, less 2), cron and audit-screen work use the lower value and the settings screen says so; WP-CLI uses the full setting. Sitemaps that could not be read are counted on the audit screen | Capping each request at the time left turned pages and sitemaps that answer in 8 to 15 seconds into timeouts on the audit screen's 8 second step, and settings above about 19 seconds never took effect (branch review R1, 2 November 2026) |
| 26 | 6 | No longer detected: not found in a later run that covered the page (site-wide issues: any full-scope run; finding 2 then required every evidence page to be read again) | A site-wide issue's evidence page that a full audit did not list and that is no longer a published page (unpublished, trashed, deleted, or a URL that is not a post and is no longer listed) counts as gone, as a 404 does; a page read as not HTML counts as read. A page still published but outside the audit (post type not audited, over the page limit, excluded) still holds the issue untouched | Otherwise a site-wide issue fixed by unpublishing one of its pages stayed present for ever, never cleared, never unavailable (branch review R2, 2 November 2026) |
