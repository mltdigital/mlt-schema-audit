# Changelog

All notable changes to MLT Schema Audit. Dates are UK dates. Versions follow semantic versioning; nothing has been released yet.

## Unreleased (0.1.0)

### Review fixes (30 October 2026)

Two code reviews on 30 October found defects to fix before any pilot. Fixed so far:

- Private-address check (review finding 1): IP addresses are now classified by their bytes, not their spelling. `::ffff:7f00:1`, `0:0:0:0:0:0:0:1`, NAT64 and 6to4 forms of loopback, private and metadata addresses were treated as public and are now refused.
- Denied paths (review finding 11): the admin, login, XML-RPC and REST deny list is now checked against the path as a server would read it (decoded, dot segments and repeated slashes removed), so `/public/../wp-admin/`, `/%2e%2e/wp-admin/` and `//wp-admin/` are refused, including in absolute redirect locations. Frozen URLs have dot segments removed.
- Site-wide issues (review finding 2): a site-wide issue (SITE-001, SITE-002, SITE-003, ID-003, URL-004) is now cleared only when every page it rests on was read again, or has gone, and, for a broken image or logo, the image was checked again or no page read still uses it. Before, any full-scope run with no matching finding cleared it, even when its pages timed out or had dropped out of scope. The evidence is stored on the issue in a new `evidence` column (database version 2). A page that could not be read, or an image over the 200-image cap, sets the issue to "Unavailable"; a page outside the run leaves it untouched. SITE-001 evidence includes every page carrying the business, not only the page that differs. Issues stored before this change clear only when every page in the run was read. The digest's "resolved" count follows the same rule.
- Image and logo checks (review finding 3): the `/wp-content/` and `/wp-includes/` deny rule stopped URL-004 checking any image in the media library, so broken uploads were never reported. Image and logo checks now use a wider path policy: static image, PDF and video files in those folders may be requested, on every redirect hop; scripts never (no `.php` or other script extension anywhere in the path, so `run.php/a.png` and `a.php.png` are refused), and page fetches still refuse both folders. Each run records images referenced, requested, checked (an answer received) and broken, shown on the audit screen and in the export summary; an image that was not checked keeps its issue open.
- Worker budget and recovery (review finding 4): no request can now outlive the worker's time budget. Each request's timeout is the lower of the timeout setting and the time left; a request the budget cut short, or a retry there was no time left to wait for, is "deferred", not recorded as a timeout. The page or image stays pending and the slice ends, so the next slice starts with it and a full budget; on its third deferral it is recorded as a timeout (reason `budget_timeout`) or an error (reason `budget_spent`). Image checks now record each attempt before the request, as page fetches already did, so an image that kills the process is given up after three attempts (reason `worker_stopped`). Sitemap discovery reads one sitemap per step, with progress in the `mltsa_discovery_state` option (removed when the run finishes and on uninstall). Each tick queues its own continuation before it starts work (budget plus 150 seconds, after the run lock has expired), so a process killed part way through no longer leaves the audit stranded; a normal finish brings it forward to 30 seconds. A new hourly `mltsa_watchdog` event requeues the worker for an active run that has no worker event, and logs `worker_restarted` against the run.
- Outbox scheduling (review finding 5): a failed send is retried 5, then 10 minutes later, but nothing queued an event for that time, so the retry waited for whatever cron event came next (on a quiet month, the next monthly run). The outbox now keeps one `mltsa_outbox` event at the moment it next has work: the earliest pending retry, or the moment a claim on an interrupted send expires. Due rows are read earliest first, so rows waiting for a retry no longer fill the per-call limit and hold back rows that are due. While mail is blocked (kill switch, no recipients, home URL changed) no event is queued; saving settings or reconfirming recipients queues one, and the hourly watchdog puts back a lost one.
- Recheck of plain permalinks (review finding 6): a recheck dropped the query string from every URL, so a page stored as `/?p=12` or `/?page_id=7` was rechecked as the home page, not as itself. Recheck URLs come from the register, which holds only URLs a full audit already froze, so they now keep their query; the request policy still refuses action, nonce and REST queries.
- Removed rules (review finding 7): the audit comparison looked for changed rules only in the current rule set, so a finding of a rule that had been removed counted as "No longer detected" in the digest while the register correctly held it. It now compares the rule IDs of both runs; findings of a removed or re-versioned rule are counted separately ("not a fix"), and an evidence change under a changed rule is counted as a rule change, not a website change.
- Commented-out JSON-LD (review finding 8): the extractor searched the raw HTML for script tags, so a block inside an HTML comment, a textarea, template, noscript, xmp, title, style or iframe, after a plaintext tag, or inside a quoted attribute value was audited as live markup. The scan now follows the HTML tokeniser's rules for those contexts, including unterminated comments, `-->` and `--!>`, and a `>` inside a quoted attribute of the script tag itself. Real script content is still read as raw text.
- CDATA wrappers (second review, ENG-1): a block wrapped as `/* <![CDATA[ */ ... /* ]]> */`, as older plugins emit, is now unwrapped and parsed. `//<![CDATA[` and plain `<![CDATA[` forms still work.
- Split definitions (second review, ENG-2): properties of one @id defined in several blocks were merged with array union, so a multi-valued property (sameAs, telephone, address, identifier and similar) kept only the first block's value and rules never saw the rest, such as a Companies House link in a second block. Multi-valued properties are now combined across definitions without repeats; single-valued ones (name, legalName, url, description) are unchanged and keep the first value.
- Filtered exports (review finding 10): the Findings screen's download link and the export handler left the search box out, so a searched view downloaded every finding, and a search on its own was labelled a full export. The sanitised search now goes through the link, the handler, the findings CSV, the summary and the manifest. A search for `0` is now applied (it was ignored). A display group with no rules now exports nothing, as on the screen, instead of everything.
- Extra staging hosts (second review, BUG-1): hosts entered under "Extra staging or development hosts" are stored as plain hosts but were run as regular expressions, so none ever matched. Each is now quoted and anchored to the whole host, and also covers its subdomains, as the built-in suffix patterns do. The finding's evidence names the host. Stored values need no change.
- Approved numbers in evidence (second review, BUG-2): the FACT-006 evidence listed approved telephone numbers as stored (without the leading zero, for example `1632960123`). It now shows them as staff enter them (`01632960123`). Matching is unchanged.
- CSV formula guard (second review, SEC-1): the guard prefixed a cell only when its first byte was `=`, `+`, `-`, `@`, tab or carriage return, so a cell starting with a space or line break before one of them (for example a newline then `=HYPERLINK(...)`) was not neutralised. It now also checks the first visible character after any spaces, control characters or Unicode whitespace (no-break and zero-width spaces, byte-order mark). Every export file writes its cells through this one guard.
- Reproducible ZIPs (second review, SEC-4): ZIP entry dates were read in the server's timezone, so the same commit built on machines in different timezones gave different checksums. They are now read in UTC. Export ZIPs and the release build both use the one writer.
- Findings export notes (second review, ENG-4): the findings export read each issue's note history with one query per issue. It now reads the latest note of every issue in one query (500 issues per query for large exports), with the same output.
- Issue register screen (review finding 9): the Findings screen lists one audit's occurrences, so after a small recheck, or a failed full audit, outstanding issues the latest run did not read dropped out of the default view and could be reached only through an older audit or a known issue ID. A new **Issue register** screen (Schema Audit, Issue register; same `mltsa_audit` capability) lists every issue across all audits from current issue state, with the latest evidence, page, severity, status, due date, owner, verification state, first and last observed. Filters: status, verification, owner (including nobody) and search; 50 per page; each row opens the issue. Per-run observations stay on the Findings screen, which now links to the register. No change to how issues are stored or cleared.
- Cancel wins (second review, BUG-5): a cancel from the audit screen while the worker was part way through a step could be written over. If it arrived during the final step, the worker saved the run as complete (or partial or failed), logged it as finished and, for a monthly run, queued its digest; in earlier steps the phase was set back from "done". The worker now saves run progress only while the run is still running, in the same statement, and checks before each page and image request, so a cancel also stops the requests. The cancel itself applies only to a run still queued or running, so a run that finished a moment earlier keeps its outcome, and the screen says nothing was cancelled.
- Private own host, www and bare forms (second review, BUG-4): with `MLTSA_ALLOW_PRIVATE_SELF` set for local development, the audit policy allows the home host and its www or bare form on a loopback or private address, but WordPress checks the URL again and exempts only the home host itself, so the other form was refused (its private address, and the home URL's own port). The request now gives that one form the same exemption, only while the constant is set and the connection is pinned to a loopback or private address; link-local and metadata addresses, other hosts and sites without the constant are refused as before. The Health screen's warning about the constant is unchanged. The reviewer's suggestion to turn WordPress's check off was not adopted.
- Broken `sameAs` links (review reply): URL-004 reports a broken image or file, but it also checked own-host `sameAs` links, so a profile page returning 404 was reported as a broken image. It now checks own-host `image`, `logo`, `thumbnailUrl` and `contentUrl` values only (URL-004 version 3, rule set 2026.11.1). A broken own-host `sameAs` page is not reported at all for now; pilot defect D44 is no longer detected (its fixture says so). A link rule would be a contract change. Open URL-004 issues for a `sameAs` link are held as a rule change, not counted as fixed. Contract revision note 22.
- Database upgrade (review reply): a new integration test builds the version 1 issues table, upgrades it and checks the `evidence` column, the data, the recorded version and a second run. It found that the upgrade recorded version 2 even when the database refused the new column (dbDelta reports the column as added either way), so it was never tried again; on the development site's SQLite layer that is what happened, because a `NOT NULL` text column cannot be added without a default. The `evidence` column is now nullable (an empty or missing value already meant "stored before evidence"), the version is recorded only once every upgraded column is present, a failed upgrade is retried hourly rather than on every page load, and the Health screen reports an incomplete upgrade.
- Repeated "unavailable" (review reply): a finding whose page or image could not be read is held as "Unavailable", and one held that way audit after audit looked like a stable result. Each audit now records how many audits in a row each issue has been held as unavailable (carried over while it is outside a recheck's scope, reset once it is read), and the audit screen and the export Summary show the number held as unavailable in that audit, the number unavailable in 2 or more audits in a row with links to them (IDs in the export), and the longest run. Read-only: no issue state or work status changes. Contract revision note 23.
- Frozen URL list saved once (open check from fix 4): discovery saves the URL list in its last step and then moves the run on; a worker killed in between left the list saved and the run still in discovery, so the next attempt listed every URL again (6 rows for 3 URLs in the test), and each page was read twice. `run_urls` has no unique key. The list is now saved in one transaction that first removes any rows an earlier attempt left, so a retry gives one row per URL. No schema change.
- Test data: telephone numbers in code comments, unit tests and three historical fixtures that were outside the Ofcom drama ranges (one may belong to a real business) are replaced with drama-range numbers (01632 960xxx, 0141 496 0xxx). The fixture check now accepts only the 01632 960xxx and 0808 157 0xxx drama ranges, not any 01632 number. Earlier commits are not rewritten.
- Own-host profile links (owner decision, 2 November 2026): new rule URL-008 "Profile link on this site returns not found" (medium). An own-host `sameAs` link is requested once per audit as a page, under the normal page policy, sharing the 200-request limit, budget, deferral and "unavailable" handling of the image and file checks; 404 and 410 are reported. Links to other websites are never requested. Pilot defect D44 is detected again, by URL-008 rather than URL-004. Rule set 2026.11.2, so open issues under the earlier rule set are compared as a rule change. The audit screen and export now say "Images, logos and profile links". Contract revision note 24.
- Size cap boundary (review reply): a page of exactly 5,242,880 bytes was reported as cut at the size cap, because a whole page and a cut one look the same at that length. The request now asks for one byte more than the cap, reports "too large" only when the response went over it, and keeps at most the cap in memory. Tests at exactly the cap and one byte over, plain and gzip.
- PHP 7.4 static check: PHPCompatibility with testVersion 7.4 over the plugin, build script and tests (44 files) reports nothing, and a token scan for PHP 8-only functions and syntax that it can miss (`str_contains` and similar, `match`, `?->`, named arguments, union, `mixed`, `static` and `never` types, enums, `readonly`, attributes, first-class callables, `new` in initialisers, constructor promotion, trailing commas in parameter lists, throw expressions, `catch` without a variable, `$object::class`) finds none. One runtime difference was found and fixed: PHP 7.4 sorts are not stable, so when two values were equally common the site-wide rules (SITE-001, SITE-002 and SITE-003) could pick a different "most common" value on PHP 7.4 than on PHP 8. Ties now keep the order the values were first seen, as on PHP 8. Not run on a real PHP 7.4.
- MySQL static check: every SQL statement the plugin builds (76: 69 database calls in the repository and installer, and the 7 table definitions) was read for SQL that SQLite accepts but MySQL 5.7, MySQL 8 or MariaDB would refuse or treat differently. Three were real and are fixed. The outbox's one-row-per-recipient key indexed the whole 254-character address, 1,016 bytes in utf8mb4, which MyISAM tables and older InnoDB row formats refuse, so the table would not have been created there; it now indexes the first 191 characters, as WordPress does. A URL over 2,048 characters (the column size) would have been cut by MySQL and a different page requested; discovery now lists it as excluded (`url_too_long`). An email address over 254 characters would have been cut in the outbox; the settings screen now refuses it. A unit test checks every index in the schema against the MySQL and MyISAM key limits. Not run on a real MySQL or MariaDB server.

Still open: every item of both reviews is now fixed or answered (BUG-3 was checked and is not a defect: the size cap counts decompressed bytes; a test now holds that). Own-host `sameAs` pages are checked again (URL-008) and a page of exactly the size cap is no longer reported as cut. What remains: (1) a run on a real PHP 7.4 (only static checks were possible here); (2) a run on a real MySQL or MariaDB server: the static check found nothing more, but the database upgrade, the transactions around the frozen URL list and the reconcile step (branch review R4), the 191-character outbox key and affected-row counts were tested on the SQLite development site only. For the owner to decide, unchanged: the www or bare form of a public site on a non-standard port is still refused by WordPress's own port rule.

### Branch review (2 November 2026)

A review of the review-fix branch found five more defects (R1 to R5), all fixed:

- Request timeout and slices (branch review R1): the finding 4 fix lowered each request's timeout to the time left in the worker's slice. The audit screen's step has 8 seconds, so with the screen open a page or sitemap answering in 8 to 15 seconds was cut short three times and then recorded as a timeout (or a sitemap given up, its pages silently left out), although it answers within the 15 second setting; and under WordPress cron no setting above about 19 seconds took effect. Now a request starts only when the slice has the full timeout left, and is never shortened, so a timeout always means the site took longer than the setting; no request outlives the slice. Every slice (WordPress cron, the audit screen's step, WP-CLI) is raised to at least the timeout plus 2 seconds (17 seconds at the default). A page, file or sitemap deferred for lack of time stays first in line and is not counted; a deferral counts only when it had the whole slice (a redirect chain or retries that do not fit one), and the third such is recorded as an error (`budget_spent`). Where the PHP time limit cannot fit the setting (limit less 10 seconds, less 2), cron and audit-screen work use the lower value and the settings screen shows a warning; WP-CLI uses the full setting. Sitemaps that could not be read (other than not found) are now counted under "Left out, with reasons" on the audit screen. Contract revision row 25.
- Site-wide issues resting on a page that left the site (branch review R2): finding 2 held a site-wide issue untouched whenever one of its evidence pages was missing from a full audit, so an issue whose page had been unpublished or deleted (often the fix itself, such as removing an old duplicate page) stayed "present" for ever; a page now served as something other than HTML had the same effect. A full audit now looks up each missing evidence page: one that an earlier audit listed as a WordPress post and that is no longer published (unpublished, trashed or deleted) counts as gone, as a page answering 404 does, and a page read as not HTML counts as read. With the other pages read, the issue is set to "No longer detected" and the digest counts it as resolved, as before finding 2. A page still published but outside the audit (post type not audited, over the page limit, excluded), or a URL never listed as a post (one found only through a sitemap may be missing just because sitemap discovery was switched off; owner decision, 2 November 2026), never clears the issue, as finding 2 requires. Such an issue is now held as "Unavailable" (it was left "present"), with a history event saying a page it rests on is outside the audit, so it counts in the repeated "unavailable" figure (owner decision, 2 November 2026). The digest, the resolved count and the export are unaffected beyond that figure: the digest carries page counts and the comparison, which counts a site-wide issue as resolved only when its evidence was read. Page-level issues are unchanged.
- Large files in image and file checks (branch review R3): a HEAD request has no body, but its Content-Length (the file's size) was compared with the 5 MB size cap, so any own-host image, PDF or video over the cap that answered 200 was recorded as "too large", counted as not checked, and its URL-004 or URL-008 issue held as "Unavailable" for ever. A HEAD answer is no longer checked against the cap (the cap applies to GET bodies), and where a server refuses HEAD, a 2xx answer to the GET fallback shows the file exists however large its body. Page fetches still report a body over the cap as too large.
- Cancel during reconcile (branch review R4): BUG-5 made a cancel win over the run row, but the register writes of the reconcile step (new issues, "No longer detected", "Returned", reopened events) were neither guarded nor grouped, so a cancel that arrived while reconcile ran left the register changed by a run that ended as cancelled, sometimes part way. The step's writes and the run's move to its final step are now one transaction (START TRANSACTION, committed only if the run is still running; otherwise rolled back), so a cancelled run never changes the register, and a worker killed part way through leaves nothing half written. Once that commit is made, a cancel is refused ("nothing was cancelled") and the kill switch lets the run finish, its email still held by the outbox, so a run whose register changes stand never reports as cancelled. Tested on the development site's SQLite with the cancel made from a second connection; MySQL row locking was checked by reading only. Contract revision row 27.
- Failed database upgrade (branch review R5): if the upgrade could not add its columns (a database user without ALTER, for example), the Health screen reported it but audits carried on against the old tables, so every new issue failed to insert, every site-wide update failed, and the run still finished complete and sent its digest. While the upgrade is pending, no audit now starts (manual, recheck, monthly or catch-up) and the worker does no work on a run already in progress (it waits; the hourly retry completes the upgrade and the run continues). Every Schema Audit screen shows the Health screen's message, a refused start says the upgrade is the reason, the audit screen's progress step stops with it, `wp mltsa audit` refuses with it and `wp mltsa tick` warns. Contract revision row 28.

A second review of the branch found five more (S1 to S5):

- Slow HEAD refusal (branch review S2): where a server answered an image or file check's HEAD request with 405 or 501 slowly (after 2 seconds on the audit screen, 5 under WordPress cron), the GET fallback had no full timeout left and was deferred without counting, although the HEAD had been sent. The next slice repeated the same HEAD, so the run never left the file checks, blocked every later audit and sent the site one HEAD per slice for ever. The HEAD and its GET fallback are now one accounted attempt, and the next slice starts with the GET (see S1), so the file is checked and the run moves on.
- Redirects and retries across slices (branch review S1): the R1 fix let a request start only with the full timeout left, but a redirect hop or a retry needed a second full timeout in the same slice. On the audit screen (17 second step) no retry ever fitted, and under WordPress cron the second did not, so a page or sitemap answering 429 or 5xx was recorded after three slices as `budget_spent` (the worker running out of time) instead of as the site refusing it, and a page or sitemap behind a slow redirect was given up although every response came inside the timeout. A deferred fetch now keeps the redirect hop, retry and backoff it reached, and the next slice continues from there; nothing is requested twice and no request is shortened or outlives its slice. A deferral counts toward the limit of three only when the URL had the whole slice and still no request could start (not while waiting for a retry's backoff), so a URL being read is never given up and a run always ends. Pages, image and file checks and sitemaps all work this way. Contract revision row 29.
- WordPress cron throughput (branch review S5): with the full timeout needed for every request, a 20 second WordPress cron slice could start requests only in its first 5 seconds and then waited 30 seconds for the next event: 4 pages per 36 seconds against about 13 per 51 seconds before the branch (measured on the development site with 0.5 second pages and default settings). A slice that ends because the next request would not fit now queues the next worker event after the usual gap between pages instead of 30 seconds, so the next page load runs it. Server cron and the audit screen were not affected.
- Monthly audit refused during an upgrade (branch review S3): a monthly start refused while the database upgrade was pending was never caught up on a site without the server cron job, because the catch-up check ran only from the worker, and plain WordPress cron runs the worker only while an audit is active. The hourly watchdog now runs the catch-up check too, so the missed month starts within an hour of the upgrade completing.

### Stage 5: monthly operations, verified

- Proven on the disposable site by `tests/integration/run.php` (16 tests): monitoring cannot be switched on until scope, recipients and schedule are confirmed, then exactly one start is scheduled; deactivation leaves no `mltsa_` event; reactivation rebuilds the next start only; a missed month runs once as a catch-up with its lateness recorded; a second start for the same month, or any start while a run is in progress, is refused; the kill switch setting cancels a monthly run without another request while manual audits still start; `MLTSA_DISABLE` stops manual starts, the worker and mail; no recipients means no mail and never `admin_email`; a clone or staging copy pauses all mail until recipients are reconfirmed; an interrupted send becomes `delivery_unknown` and is never resent; failures retry at most three times; a recipient change rebuilds unsent notifications.
- Added `Settings::reconfirm_recipients()`, logged with both addresses, for lifting the clone pause.
- Deactivation now forgets when monitoring started, so a reactivation never catches up a month missed while the plugin was off.

### Stage 4: manual workflow

- Admin screens under Schema Audit: Audits (start, live progress, run list), one audit (coverage, exclusions with reasons, comparison with the previous audit, pages), Findings (filters by audit, group, severity, outcome, status, rule and text; recheck of ticked findings), one finding (rule explanation, evidence as plain text, work status, owner, due date, external link, exception reason, reviewer and date, notes, history), Settings and Health.
- Work statuses as the contract lists them; an accepted exception or false positive needs a reason, a reviewer and a review date. Verification state is set only by the scanner, and marking a finding Resolved does not verify it.
- Export: a ZIP of Summary, Pages, Findings and Change log CSV files plus `manifest.json`, or any CSV on its own, streamed from memory (a small ZIP writer, because ZipArchive needs a file on disk). Filtered exports say so in the manifest and the Summary sheet. Cells that start with `=`, `+`, `-`, `@`, tab or carriage return are neutralised; every cell is quoted, so leading zeros and line breaks survive; UTF-8 with a byte-order mark.
- Recheck: starts a run for the pages behind selected findings, using page URLs from the register, never from the request. Site-wide findings are rechecked by a full audit.
- Every handler checks a capability and a nonce first; there are no REST routes and nothing for logged-out users. While an audit screen is open, a script keeps the audit moving in short steps (text only, never markup).

### Stage 3: the plugin activates and audits

- Settings in one option (`mltsa_settings`, not autoloaded), sanitised on save, with every change logged to the event table. Recipient changes are logged as counts only and confirm the recipients on the current home URL.
- Monthly calendar maths (first to fourth or last weekday, local time, explicit timezone) in a pure class with a schedule key per month.
- Scheduler: one single event for the next occurrence, catch-up for a missed occurrence (never a backlog), start mutex, and refusal of a second run while one is in progress.
- Repository: every query in one class, all variables prepared.
- Discovery: homepage, published posts of chosen public types, optional capped same-host sitemaps; exclusions recorded with reasons; drafts and private content never queried.
- Resumable worker: discover, fetch, site rules, resource checks, reconcile, notify. One request at a time, gap between requests, longer waits when the site is slow, a lock per run, and every URL written once.
- Outbox, digest and retention classes (completed in stage 5).
- WP-CLI: `wp mltsa tick`, `wp mltsa audit [--wait]`, `wp mltsa status`.
- Fixed: the HTTP client read response headers by casting the Requests header dictionary to an array, which returned its private storage, so `Location` and `Content-Type` were never seen and every redirect was recorded as an HTTP error.
